# Руководство по базе знаний

База знаний — четыре CSV-файла в каталоге `knowledge_base/`. Их можно редактировать без изменения Python-кода: изменения подхватываются после перезапуска бота.

## Архитектура

```text
knowledge_base/*.csv
        │  чтение (только чтение, UTF-8)
        ▼
CsvKnowledgeRepository          app/knowledge/csv_repository.py
        │  строки → Pydantic DTO (KnowledgeItem, StarExample, ChecklistItem, ProfessionProfile)
        │  невалидные строки пропускаются с предупреждением в логе
        ▼
KnowledgeService / ChecklistService     app/services/knowledge_service.py, checklist_service.py
        │  кэш в памяти, отбор по профессии, категории и ключевым словам
        ▼
Business Service                 QuestionService, AnswerService, Telegram handler чек-листов
        │
        ▼
OpenAIService (вопросы, STAR-примеры) / Telegram (чек-листы)
```

Правила слоёв:

- Telegram handlers не читают CSV и не импортируют `app.knowledge`; они получают данные только через сервисы.
- Репозиторий ничего не пишет в CSV.
- Если файл отсутствует или повреждён, сервис возвращает пустой список, пишет предупреждение в лог, и бот продолжает работать без этого источника.
- Vector database, embeddings и RAG не используются: отбор детерминированный.

## Файлы

| Файл | Что хранит | Где используется |
|---|---|---|
| `professions.csv` | реестр профессий: код, название, псевдонимы в названиях вакансий | определение профессии вакансии; названия в чек-листах; проверка кодов профессий |
| `questions.csv` | типовые вопросы собеседования | `QuestionService` → блок `<knowledge_base>` промпта `questions.txt` |
| `star_examples.csv` | образцы ответов по STAR | `AnswerService` → блок `<star_examples>` промпта `answer_analysis.txt` (только для STAR-вопросов) |
| `checklists.csv` | пункты чек-листов подготовки | раздел «📋 Чек-листы» в Telegram, без OpenAI |

## Общие правила заполнения

- Кодировка **UTF-8** (Excel: «CSV UTF-8 (разделитель — запятая)»). Разделитель колонок — запятая.
- Первая строка — заголовок с точным набором колонок; порядок колонок не важен, лишние и недостающие колонки считаются ошибкой.
- Если значение содержит запятую, кавычки или перевод строки, заключите его в двойные кавычки: `"Как вы собираете требования, если заказчик недоступен?"`. Двойная кавычка внутри значения удваивается: `""`.
- **Списки** (`keywords`, `aliases`) разделяются точкой с запятой: `"BPMN;процессы;моделирование процессов"`. Запятая тоже принимается как разделитель, но `;` предпочтительнее. Пустых элементов (`a;;b`) и повторов (`SQL;sql`) быть не должно.
- `id` уникален внутри файла. Не меняйте `id` существующих строк.
- Коды (`profession`, `category`, `difficulty`, `priority`) пишутся латиницей в нижнем регистре (регистр при чтении нормализуется).
- Пустых строк быть не должно.
- Все тексты — на языке пользователей бота (сейчас русский).

## professions.csv

| Колонка | Обязательна | Значения | Описание |
|---|---|---|---|
| `profession` | да | `^[a-z][a-z0-9_]*$` | код профессии, на который ссылаются остальные файлы |
| `title` | да | текст | название для пользователя (показывается в чек-листах) |
| `aliases` | да | список через `;` | фрагменты названий вакансий, по которым определяется профессия |

Как работает сопоставление: название позиции из анализа вакансии приводится к нижнему регистру; профессия считается совпавшей, если любой псевдоним встречается в названии как подстрока. Пример: позиция «Senior Python-разработчик» совпадает с `technical` по псевдониму `разработчик`.

Советы:

- Используйте основы слов, чтобы покрыть падежи и формы: `менеджер проект` покрывает «Менеджер проектов», «менеджер проекта».
- Добавляйте английские и русские варианты.
- Не используйте слишком короткие псевдонимы (`qa` совпадёт и с другими словами, где встречается «qa»): проверяйте на реальных названиях вакансий.
- Код `general` зарезервирован для общих пунктов чек-листов; не объявляйте его как профессию.

## questions.csv

| Колонка | Обязательна | Значения | Описание |
|---|---|---|---|
| `id` | да | строка, уникальная | например `53` |
| `profession` | да | код из `professions.csv` | профессия вопроса |
| `category` | да | `technical`, `behavioral`, `situational`, `experience` | тип вопроса |
| `question` | да | текст | формулировка вопроса |
| `difficulty` | да | `easy`, `medium`, `hard` | сложность |
| `star_required` | да | `true` / `false` (принимаются также `1`/`0`, `yes`/`no`, `да`/`нет`) | нужен ли ответ по STAR |
| `keywords` | да | список через `;` | навыки и темы, по которым вопрос находится |

Категории:

- `technical` — знания и инструменты профессии («Как вы описываете процесс в BPMN?»);
- `behavioral` — прошлое поведение («Расскажите о случае, когда…»), обычно `star_required=true`;
- `situational` — гипотетическая ситуация («Что вы сделаете, если…»);
- `experience` — опыт и достижения («Какой проект вы считаете самым успешным?»), обычно `star_required=true`.

Исторические значения `sql` и `requirements` в строках 3 и 4 читаются как `technical` (обратная совместимость). В новых строках их не используйте.

Как вопрос попадает в промпт: `QuestionService.collect_keywords()` собирает ключевые слова вакансии из `hard_skills`, `soft_skills`, `interview_topics` и `responsibilities`. `KnowledgeService.find_relevant()` начисляет +3 за совпадение профессии, +2 за категорию, +1 за каждое совпавшее ключевое слово. Однословное ключевое слово должно совпасть со словом вакансии целиком (`SQL`), многословное — как фраза (`моделирование процессов`). Вопрос без совпадения профессии и ключевых слов не выбирается. В промпт попадают до 20 вопросов с наибольшим баллом, дубликаты удаляются.

Рекомендации: на каждую профессию — не меньше 3 вопросов каждой категории; ключевые слова берите из формулировок реальных вакансий.

## star_examples.csv

| Колонка | Обязательна | Значения | Описание |
|---|---|---|---|
| `id` | да | строка, уникальная | например `STAR-015` |
| `profession` | да | код из `professions.csv` | профессия примера |
| `category` | да | `behavioral`, `situational`, `experience` (`technical` допустим, но не используется: STAR-примеры подбираются только для STAR-вопросов) | тип вопроса |
| `question` | да | текст | вопрос, на который отвечает пример |
| `situation` | да | текст | контекст: где, когда, какая проблема |
| `task` | да | текст | личная задача героя примера |
| `action` | да | текст | конкретные действия от первого лица |
| `result` | да | текст | измеримый результат |
| `keywords` | да | список через `;` | темы, по которым пример подбирается |

Правила:

- Пример — **вымышленный** эталон структуры. Модели запрещено переносить его факты в разбор ответа кандидата, поэтому не пишите реальные компании и персональные данные.
- Каждый элемент STAR — 1–2 предложения; в `result` — число или проверяемый итог.
- Одинаковую `situation` в двух примерах валидатор считает дублем.
- В промпт попадает не больше 2 примеров; ID примеров в OpenAI не передаются.

## checklists.csv

| Колонка | Обязательна | Значения | Описание |
|---|---|---|---|
| `id` | да | строка, уникальная | например `CL-051` |
| `profession` | да | `general` или код из `professions.csv` | общий пункт или пункт для профессии |
| `category` | да | см. ниже | раздел чек-листа |
| `title` | да | короткий текст | заголовок пункта |
| `item` | да | текст | что конкретно сделать |
| `priority` | да | `high`, `medium`, `low` | `high` отмечается ❗ как обязательный |
| `keywords` | нет | список через `;` | служебные метки, в Telegram не показываются |

Категории в порядке показа:

| Код | Кнопка в Telegram |
|---|---|
| `before_interview` | 📝 До интервью |
| `documents` | 🎒 Что взять с собой |
| `appearance` | 👔 Внешний вид |
| `final_check` | ✅ Проверка перед началом |
| `during_interview` | 💬 Во время интервью |
| `end_interview` | 🤝 Завершение интервью |
| `after_interview` | 📬 После интервью |

В разделе сначала выводятся общие пункты (`general`), затем «🎯 Дополнительно для отдельных профессий» с названием профессии из `professions.csv`. Внутри групп пункты отсортированы по приоритету. Одинаковые `profession + category + title` считаются дублем. Раздел без пунктов в меню не показывается. Прогресс пользователя не хранится.

## Проверка базы знаний

```powershell
python -m app.knowledge.validate
```

Команда проверяет кодировку, заголовки, количество колонок (частая причина — запятая без кавычек), пустые строки и обязательные поля, допустимые значения, разделители списков, коды профессий, уникальность `id` и дубли. Пример вывода:

```text
Knowledge base has 1 problem(s):
  - questions.csv:54: expected 7 columns, got 8 (check quotes and commas)
```

Для другого каталога: `python -m app.knowledge.validate path/to/dir`. Эта же проверка выполняется в тестах (`tests/test_knowledge_data_quality.py`), поэтому сломанная база не пройдёт `python -m pytest`.

## Пример: новая профессия «UX Researcher»

1. `professions.csv`:

   ```csv
   ux_researcher,UX-исследователь,"ux researcher;ux-исследовател;user researcher;исследователь пользовател"
   ```

2. `questions.csv` — в примере по 1–2 вопроса на категорию; в рабочей базе добавьте не меньше 3 на каждую:

   ```csv
   53,ux_researcher,technical,"Как вы выбираете между глубинными интервью, опросом и юзабилити-тестированием?",medium,false,"методы исследований;интервью;юзабилити-тестирование"
   54,ux_researcher,technical,"Как вы определяете размер выборки для качественного исследования?",medium,false,"выборка;качественные исследования"
   55,ux_researcher,behavioral,"Расскажите о случае, когда результаты исследования изменили решение команды.",medium,true,"инсайты;влияние на продукт"
   56,ux_researcher,situational,"Что вы сделаете, если продакт-менеджер просит подтвердить уже принятое решение исследованием?",hard,false,"стейкхолдеры;предвзятость"
   57,ux_researcher,experience,"Какое исследование вы считаете самым полезным в своей практике и почему?",medium,true,"опыт;исследование"
   ```

3. `star_examples.csv`:

   ```csv
   STAR-015,ux_researcher,behavioral,"Расскажите о случае, когда результаты исследования изменили решение команды.","Команда планировала редизайн личного кабинета, считая главной проблемой устаревший интерфейс.","Мне нужно было за две недели проверить гипотезу и найти реальные причины оттока.","Я провела 10 глубинных интервью и юзабилити-тест с 6 участниками, сгруппировала наблюдения в карту инсайтов и показала команде видеофрагменты.","Команда отказалась от полного редизайна и исправила 3 сценария оплаты; отток за квартал снизился на 9%.","инсайты;интервью;юзабилити-тестирование"
   ```

4. `checklists.csv` — пункты для профессии:

   ```csv
   CL-051,ux_researcher,documents,"Кейсы исследований","Подготовьте 2–3 кейса: цель, метод, выборка, ключевые инсайты и что изменилось в продукте.",high,"портфолио;кейсы"
   ```

5. Запустите `python -m app.knowledge.validate`, затем `python -m pytest`.
6. Перезапустите бота и проверьте вакансию «UX Researcher»: в логе должно быть `Knowledge base questions loaded`, а вопросы — соответствовать профессии.

## Перенос в Google Docs / Google Sheets

Интеграции с Google API в проекте нет: бот читает только локальные CSV-файлы. Google Sheets удобно использовать как редактор.

**Выгрузка в Google Sheets:**

1. Google Drive → «Создать» → «Google Таблицы» → «Файл» → «Импорт» → «Загрузка» → выберите CSV.
2. Тип разделителя — «Запятая»; снимите галочку «Преобразовывать текст в числа, даты и формулы», чтобы `id` и ключевые слова не изменились.
3. Каждый CSV-файл — отдельный лист или отдельная таблица с тем же именем.

**Возврат в проект:**

1. «Файл» → «Скачать» → «Формат CSV (.csv)»: выгружается только текущий лист.
2. Сохраните файл в `knowledge_base/` с исходным именем (`questions.csv` и т. д.). Google сохраняет CSV в UTF-8.
3. Запустите `python -m app.knowledge.validate`, исправьте ошибки, затем `python -m pytest`.
4. Закоммитьте изменения CSV в git.

Не переименовывайте и не удаляйте колонки заголовка, не добавляйте строки-итоги и примечания в ячейки под таблицей.

**Google Docs** подходит для документации (`docs/*.md`): «Файл» → «Открыть» → загрузите `.md` (или вставьте текст). Источником правды остаются файлы в репозитории; после правок в Google Docs перенесите текст обратно в `.md`.
